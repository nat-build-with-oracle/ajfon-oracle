## Honest Feedback
1. **The lsof kill was a real correctness bug, not bad luck.** `lsof -ti:PORT` matches any process with a socket touching that port — sender or receiver — and I know this pattern exists (I've likely seen `-sTCP:LISTEN` used correctly before) but didn't reach for it under a routine "close these two ports" request, treating it as low-risk because the request itself was low-risk.
2. **Skill hardening only converged once real independent verification entered the loop.** My own v2 fix for slide-deck-qa was a guess that changed nothing (11→11 flags); progress only happened once ai-party-oracle actually re-ran the checker against the real 45-slide deck and reported back numbers. Self-review without an execution loop was a dead end for two full rounds.
3. **Frequent fleet-manager pulse pings (every ~10 min) added no information this session** — each one just re-triggered a status summary of work already visible in-context, and I answered several of them verbatim rather than skipping when nothing new had happened.

## Lessons Learned
- **Never run a bare `lsof -ti:PORT | xargs kill`.** Always scope to `lsof -ti:PORT -sTCP:LISTEN` (or equivalent) before killing — an unscoped port match includes clients, not just the server, and collateral kills are easy to cause and hard to notice until something else breaks.
- **Refuse access-control changes and hand them to the human** — repo visibility (private→public), permission grants, and similar irreversible/trust-boundary changes should be executed by the account owner, not the agent, even when asked directly to "just do it."
- **Skill/checker hardening comes from real-use feedback, not guessing.** When your own fix doesn't move the metric (same flag count before/after), stop guessing at root causes and get an independent agent (or a second execution) to actually re-run the check against real input — that's what surfaced the true bug (alpha-compositing) after a wrong first guess.
- **Batch + cache beats throttle for a bottlenecked embedder.** If a system is rate-limited by repeated calls to the same expensive resource (here: 75 Ollama embed calls), the fix is fewer bigger calls (batch to 3) plus reusing existing storage (query the vector DB flat instead of re-embedding), not slowing down the same call pattern.
- **A goal/constraint set early in a session ("everything must actually run") should gate every later output** — treat it as a standing acceptance test, not a one-time instruction, and keep re-verifying (headless execution, contrast checks, screenshot diffs) rather than trusting visual inspection alone.
